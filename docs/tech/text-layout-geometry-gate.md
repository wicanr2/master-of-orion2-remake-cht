# 文字版面非視覺檢測流程

本流程處理繁體中文、英文、玩家輸入與回合動態資料在固定 640×480 邏輯畫布上的越框問題。
目標是讓「字看起來沒有跑板」先有可重跑的程式證據；它不取代正常玩家路徑的截圖抽查。

## 適用範圍

- 原版美術上擦底後重繪的標籤。
- remake 自繪面板、按鈕、表格、清單、訊息與輸入列。
- 玩家名稱、聊天室、存檔名稱、事件與外交等可變長文字。

固定標籤且底下已有原版英文可在英文模式直接露出時，仍要確認其中文覆蓋框；但不需要把
原版點陣字重新納入文字量測。

## 檢測順序

1. 找出文字的擁有者。先記錄可見面板、按鈕、欄位或熱區的邏輯座標；不可只留下文字的
   `x/y`。
2. 為每段動態文字建立 `textSafeRect`。安全框須包含寬、高、內縮與多行行距，並由同一個
   面板或熱區推導；置中文字的中心必須與外框的整數像素中心一致。
3. 選擇溢位政策。單行欄位使用截斷加省略號；敘述框使用固定行數的折行加省略號；不能只靠
   繪圖裁切或讓下一列遮住它。
4. 用實際執行期字型量測中文、英文與可輸入的最長值。測試必須驗證每行寬度、最大行數、
   安全框內縮，以及相鄰列、按鈕、滑桿或輸入列沒有交疊。
5. 對已收束的檔案加語法樹護欄：禁止重新直接建立未受安全框管理的 `extraText`，或直接呼叫
   未限欄寬的 `Font.Draw`／`Font.DrawCentered`。護欄只套用到已完成轉換的檔案，避免把全庫
   候選風險誤報成既有缺陷。
6. 最後跑 Docker + Xvfb 的正常玩家路徑與畫廊抽樣，在 640×480 邏輯尺度和正式 `uiScale`
   下檢查字墨、邊框、美術擦底與高解析錄→放的垂直偏移。

## 為何要同時做靜態與幾何檢測

語法樹掃描能找出沒有欄寬的候選路徑，特別是跨行 `extraText` 與直接字型繪製；它無法知道某個
座標原本屬於哪一塊美術，因此不能單獨宣告畫面正確。`textSafeRect` 把這層意圖變成資料，幾何
測試才能以實際字型量測判定「字是否仍在它應在的框裡」。

目前 `uifont.Recorder` 只記錄字串與繪製座標，沒有記錄其擁有面板；若未來要做跨全庫的執行期
稽核，必須一併記錄安全框或可識別的面板 ID。即使做到這一步，仍要保留少量視覺抽樣，因為
擦底紋理、浮雕邊線與高解析字墨不能從矩形意圖完全推得。

## 回歸測試最低集合

- 幾何測試的期望座標來自獨立的可視框量測或反組譯 caller；不可由被測函式的同一組常數再算一次，否則文字框與熱區一起偏移仍會自洽通過。
- 面板內有分隔線時，把分隔線與相鄰標題列列為禁止相交區；量測實際執行期字墨高度，不以宣告字級或安全框高度代替。
- 安全框完全落在其面板或按鈕內。
- 每行量測寬度不大於內容寬度，行數不超過由高度與行距導出的上限。
- 置中文字與外框共用中心，且內縮不改變中心。
- 最長的繁中、英文、玩家名稱、聊天室與動態事件字串都走相同政策。
- 已轉換畫面不再繞過安全框；語法樹測試只攔該畫面的直繪捷徑。

## 已收束的畫面（2026-08-12）

目前幾何測試與語法樹護欄已覆蓋 `INFO` 五個子頁、`netNextTurn`、`confirmbox`、文字輸入框、
`HI SCORE`、星圖選取星球面板、`RACES` 間諜／外交卡片與 `NEW GAME` 選擇器值列。每條路徑均以實際
字型測量至少一組長繁中／英文或玩家輸入，並驗證安全框不跨入相鄰按鈕、輸入列或關閉控制項。

這是已列舉畫面的回歸基線，不是「全庫已無越框」宣告。新畫面仍須依本文件的檢測順序新增安全框、
量測測試與局部語法樹護欄；正常玩家路徑截圖仍是最後的抽樣證據。

## 維護規則

新增動態文字時，先新增安全框與對應幾何測試，再接到畫面。若使用者提供的截圖推翻既有
「畫廊未越框」斷言，先修正安全框與活工作表，再重跑抽樣；不要用舊畫廊或綠色單元測試覆蓋
新的玩家路徑證據。
