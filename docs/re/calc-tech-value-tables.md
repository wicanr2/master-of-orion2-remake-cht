> 對應 `docs/re/calc-tech-value.md` 階段 B 的三張表。來源:

## 0. 解碼方法與一個必須修正的坑

反組譯清單裡,`.data` 段的 4-byte 欄位只要數值恰好等於某個已知位址,IDA 就會把它顯示成
`offset labelname[+N]`(符號化),而不是印出十六進位常數——**不管那 4 個 byte 在語意上
是不是真的指標**。這三張表的欄位大多是小整數(topic/category 這類 0~200 的數字),
但只要幾個欄位湊出來的 32-bit 值,恰好落在可執行檔已知的程式碼/資料位址範圍內,
IDA 就會「誤讀」成一個指標符號。

第一版解碼器把所有 `offset X` 一律當成「不重要的指標欄位」填零,結果在 212 筆的表③裡
撞出 41 筆錯誤——逐一檢查後發現:錯的那 41 筆,清一色是那個位置剛好被 IDA 符號化成
`offset off_180006`、`offset loc_F0100` 這類「巧合像指標」的東西,而**這些符號名�稱本身
就內嵌著真正的位址**(`off_180006` = 位址 `0x180006`,`loc_F0100` = 位址 `0xF0100`,以此類推)。
把這個規則加回去(`offset labelname[+N]` 一律還原成 `labelname 的位址 + N`,而不是填零)之後,
表③與現成抄本的吻合率從 171/212 直接跳到 211/212——**這不是「調整到吻合」,是修正一個
先前對 IDA 顯示慣例的錯誤假設**,修正後仍然留了 1 筆吻合不了(見第 2 節)。

驗證方式:反組譯清單裡,凡是 IDA 自己標了名字的位置(`byte_17E082`、`off_17E0EE`、
`off_17E7F0`、`off_17EA60`、`dword_17EB2A`、`off_17EB3D`……這些名字本身就是它們的真實位址),
用我的逐位元組計數器重新推算一遍,**每一個都精確落在正確位址上,無一失準**——這證明
整段 2756 bytes 的位元組計數是對的,後面若有個別欄位讀不對,問題只會是「這一小段的符號
解讀」,不會是「累積長度算錯」。

## 1. 表①:研究等級基礎權重(`dword_18360C` / `_tech_research_level_values`)

- 位址:`0x18360C`;asm 行號:**553951**(`dword_18360C dd 0`)開始,連續 5 行 `dd` 到
  **553955** 結束,553956 行是下一個符號 `byte_183684`(邊界確認乾淨)。
- 索引方式:`[min(topic_tier, 22) * 4]`(呼叫端把主題等級 clamp 到 22)。
- 筆數:**30**(索引 0..29 全部有值,雖然函式實際只會用到 0..22 這 23 筆,其餘 23..29
  是表尾多出來的資料,原始碼裡可能對應更高等級但呼叫端從沒用過)。
- 純數字序列,無 `dup`/`offset` 混雜,解碼沒有歧義。

```go
var TechResearchLevelValues = [30]int{
	0, 1, 3, 6, 12, 22, 36, 62, 102, 172,
	292, 492, 812, 1372, 2372, 3972, 6372, 9972, 10400, 10800,
	11200, 11600, 12000, 12400, 12800, 13200, 13600, 14000, 14400, 14800,
}
```

數列形狀:0..17 級是接近指數成長(每級略小於 ×1.7),18 級之後(10400 起)轉成等差
(每級 +400),形狀很像「早期研究等級用倍增拉開差距、後期等級改用等差避免數字爆炸」,
但這只是形狀觀察,函式怎麼「用」這個權重(乘進 `ecx`/`edi` 的順序)已在 `calc-tech-value.md`
階段 B/H 記錄過,這裡不重複。

## 2. 表②:category 預設倍率(`byte_17D196` / `_tech_categories` + 緊接的 `byte_17D197`)

- 位址:`0x17D196`;asm 行號:**549642**(`byte_17D196 db 32h`)開始,到 **549648**
  (最後一個 `db 0`)結束,549649 行是下一個符號 `byte_17D1F9`。
- 索引方式:`byte_17D196[category*2]` = 欄位 A,`byte_17D197[category*2]` = 欄位 B
  (`byte_17D197` 是 `byte_17D196` 的下一個 byte,兩者合起來看就是同一個 flat byte
  array,pair 起來對應每個 category 兩個欄位)。
- 總長度:**99 bytes**。99 是奇數,拆成 2-byte pair 之後是 **49 組完整 pair**(category
  0..48)+ **1 個落單的 byte**(值 0,已用第 6 節的自我驗證交叉確認過是尾端填充,不是
  第 50 組 pair 的一半)。
- **關鍵交叉驗證**:category 24..48 這段裡,`0x2A..0x30`(42..48)全部是 `(0,0)`——
  對照表③實測到的 category 最大值剛好是 **41**(見第 3 節),也就是說「有意義的資料
  剛好在 41 結束,42 起面全是填充值 0」,兩張表各自獨立解碼卻在同一個邊界對上,

## 4. 自我驗證結果

比對對象:`internal/gamedata/orig_research_table.go` 的 `OrigTechTopicTable`(212 筆)。

- **比對筆數:212**。
- **吻合:211 筆(99.5%)**,包含全表唯一的 sentinel(techIdx=125,兩邊都是「無歸屬」——
  我這邊原始位元組是 `0xFFFF`,對照表用 `-1`,語意一致)。
- **不吻合:1 筆(techIdx=29)**:
  - 我解出來的 topic = **889**(原始 4 bytes:`79 03 01 00`)。
  - `OrigTechTopicTable[29]` = **70**。
  - 獨立交叉查證(不是只信任這一份對照表):`internal/gamedata/enums.go` 定義
    `TECH_BIOMORPHIC_FUNGI Technology = 29`;`internal/gamedata/techtree.go` 的
    `researchChoices[70]`(`TOPIC_TRANS_GENETICS`)清單裡就有
    `TECH_BIOMORPHIC_FUNGI`——這條資訊來自 openorion2 的 `tech.cpp`,跟
    `OrigTechTopicTable` 是完全不同的兩個來源,兩邊都指向「techIdx=29 應該屬於主題
    70」,可信度很高。

  **這一筆的原始資料本身查起來是這樣**:asm 550625 行是
  `dd offset jpt_10376+3`。`jpt_10376` 是 cseg01(程式碼段)裡一個真正的 switch 跳轉表
  (asm 68 行 `jpt_10376 dd offset def_10376`,329 行 `jmp cs:jpt_10376[eax*4] ; switch jump`),
  跟 dseg02(資料段)裡這張 tech-item 表毫無關係——**這是本文件第 0 節說的那種「巧合
  撞到已知位址」的狀況,但這次巧合本身可能就是 IDA 對這 4 個 byte 的解讀有問題**:
  按 `label+N` 的標準還原規則,這 4 bytes 應該是 `0x10376+3=0x10379` 的小端序位元組,
  但這樣算出來的 topic(889)超出合法值域(合法範圍 0..82),不像是遊戲真的會寫進執行檔
  的資料。

  我核對過:這筆紀錄前後的欄位(offset 7..10 的預設指標欄、offset 11..12 遞增序列)都
  完全正常(`w11` 在 techIdx=26..31 這段是連續遞增的 27,28,29,30,31,32,在 techIdx=29
  這筆也不例外,值是 30=29+1),只有 offset 0..3 這個 dword 讀出來的值跟已知答案對不上。
  換句話說:**問題精確侷限在這一筆記錄的頭 4 個 byte,不是位移算錯,也不是這幾份對照
  表本身有錯(兩個獨立來源都說是 70)**。可能原因:
  1. IDA 對這個位置的「像不像指標」判斷本身有 bug/誤判,顯示出來的符號名稱跟實際
     儲存的 raw bytes 不一致(這是唯一在「只讀文字檔」限制下解釋不通、需要之後直接讀
     `.exe` 原始位元組才能排除的可能);
  2. 或者這份反組譯清單在這個位置有轉錄/版本差異(不同批次反組譯結果不一致)。

  **沒有把它「修正」成 70**——表格裡照實填 889,並在這裡完整記錄推理過程,留給下一輪
  用原始 exe bytes(而不是 IDA 文字清單)驗證。

**結論**:211/212 吻合,而且吻合的方式包含了一次方法論修正(offset 符號誤填零 →
還原成真實位址)和多個獨立的表尾邊界巧合(表②的 42..48 全零 vs 表③的 category 上限
41;`word_17EB43` 恰好卡在 212*13 的位置)。這些交叉點都不是靠對答案湊出來的,是表結構
本身的自洽性——**表①②③的解碼方式可信度高,唯一例外是第 4 節詳列的 techIdx=29**。

## 6. 誠實留白

1. **表③ techIdx=29 的 topic 值(889)與已知答案(70)不吻合**,已在第 4 節完整記錄
   推理過程與兩個獨立交叉證據。**沒有把它改成 70**——這是刻意的,因為當前只讀文字檔,
   無法排除「IDA 對這 4 bytes 的符號化顯示本身有誤」這個可能性。下一輪如果要解決,
   需要直接讀 `.exe` 在檔案偏移(對應虛擬位址 `0x17E1F8`)的原始 4 bytes,繞過 IDA 的
   符號化顯示層。

2. **表②最後一個落單 byte(索引 98,值 0)的身分不確定。** 從「99 是奇數、49 組
   pair 用掉 98 bytes、剩 1 byte」的算術上看像是對齊填充,而且值剛好是 0(跟 category
   42..48 的填充值一致),但沒有直接證據證明它不是「第 50 組 pair 的殘缺開頭」——
   只是這個解讀機率極低(因為緊接著的下一個符號 `byte_17D1F9` 是完全不相關的別的
   資料,不是這張表的延伸)。標記為「很可能是填充,但未 100% 排除」。

3. **表③每筆記錄裡,topic/category 以外的其他 8 個 byte(offset 2/4/5/6/7-10/11-12)
   完全沒有解讀語意。** 這次任務範圍只要求 topic 與 category,其餘欄位的數值在解碼
   過程中順手保留了(例如 offset 11-12 那個 word 呈現「techIdx+1」的規律,offset 7-10
   多數是同一個預設指標 `dword_178A04`,少數記錄指向別的位址),但**沒有去推論這些
   欄位實際代表什麼**——這超出本次任務,留給之後需要用到這些欄位時再處理。

4. **category 42..48(表②裡的零值区)是「這個 enum 就是 0..41 共 42 種」的直接證據,
   還是「表②比表③目前觀察到的 category 範圍多留了一點餘裕,42 以上其實還有分類、
   只是這 212 筆 tech-item 剛好沒用到」,無法從這兩張表本身分辨。** 由於表②總長度
   （49 組 pair)本身也可能只是配置上湊出來的大小,不代表 category enum 真的正好是
