# 載入／儲存遊戲彈窗 IDA 與文案稽核（2026-08-26）

## 問題

既有 `loadgame.go` 已有十格存讀檔流程，但玩家文案仍以 `tr(中文, English)` 內嵌，槽位、
按鈕及錯誤訊息也直接呼叫字型，沒有雙軸文字安全框。舊 `01-gap-report.md` 同一段又同時寫了
「已完成」與「只有載入沒有儲存」，必須先重新核對原版入口與共用關係。

## 輸入與位址契約

- 輸入：`Orion2.exe`，SHA-256
  `7ae2ac2e5904ca330009af2827279d889906b0b9b7a8854c38eb707a56e955b5`。
- IDA 資料庫：`Orion2.exe.i64`，SHA-256
  `4a01791fcf877ed87a740a54748694ab34a02675e3117dac052aeaa3f883944e`。
- 工具：IDA Pro 9.4，`metapc`；本文位址為 IDA DOS/4GW image 線性位址。
- 非破壞性匯出器：`tools/ida/audit_load_save_popup_ui.py`。輸出保留 raw `sub_*` 名、函式
  邊界、caller、bytes、指令及資料參照；本文語意不覆蓋資料庫原名。

## 已證實

- `sub_7E154 @ 0x7E154..0x7E511` 是遊戲中儲存彈窗流程。它在 `0x7E198` 呼叫
  `sub_6F865` 設定儲存 help，在 `0x7E1CC` 將 `sub_7F206` 註冊為繪製回呼，並於
  `0x7E49D` 直接重繪同一函式。
- `sub_804B7 @ 0x804B7..0x80556` 是主選單讀檔入口；caller 為
  `sub_810C7 @ 0x81136`。它呼叫 `sub_7E913`、`sub_803D9`、`sub_80556`，再進入
  `sub_7DA76` 的讀檔輸入迴圈。
- `sub_7DA76 @ 0x7DA76..0x7DD41` 在 `0x7DAC6` 呼叫 `sub_6F850` 設定讀檔 help，
  並在 `0x7DAF4` 同樣註冊 `sub_7F206`。因此讀檔與存檔確實共用繪製回呼，差異位於 help、
  按鈕動作與輸入後續，不是兩套畫面。
- `sub_7E913 @ 0x7E913..0x7EA5C` 依序讀取資源字串 ID `0xBE..0xC9`；
  `sub_80556 @ 0x80556..0x80658` 以 `0x25` bytes 為槽位文字 stride 並掃描 `0x0A`
  個槽位。`sub_7DA76` 的輸入掃描亦以 `cmp ax, 0Ah` 限制十格。
- `sub_803D9 @ 0x803D9..0x804B7` 連續以資產 ID `0x14..0x1A` 載入
  `GAME.LBX`，即背景、兩顆按鈕及單人／熱座／網路／數據機四種圖示。
- `sub_7F206 @ 0x7F206..0x7F701` 是共用繪製函式。它以 `0x25` bytes 逐槽讀文字，
  在 `0x7F6ED` 每列增加 `0x1F`（31）像素，並於 `0x7F6F1` 比較十列。

## 強推論與外部交叉驗證

- `GAME.LBX#20..26` 的語意順序、視窗置中公式、槽位 `(22,22+31×i,232,27)`、
  動作鈕 `(37,337)` 及取消鈕 `(171,338,68,22)` 來自 openorion2
  `LoadGameWindow::initWidgets`，並與上述 IDA 資產序列、十列及 31px 步距獨立吻合，列為強推論。
- 原版資源 ID `0xBE..0xC9` 的逐語言實際內容本輪未從字串封存檔逐項解碼；remake 的雙語槽位
  文案改由 `assets/i18n/ui.json` 提供，不將目前譯文冒稱原版逐字字串。
