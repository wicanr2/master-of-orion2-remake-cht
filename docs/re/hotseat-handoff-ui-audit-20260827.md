# 熱座交接畫面 RE 稽核（2026-08-27）

## 問題與舊歧義

`cmd/moo2/hotseat.go` 原先把 remake 的逐席隱私交接視窗直接稱為原版
`Hotseat_Screen_ @ 0x628E2`，並把其版面註解寫成原版交接畫面的尺寸與文字錨點。
這項對應沒有 caller 與控制流證據，必須在文案外部化前重新核對。

## 證據契約

- 輸入：`Orion2.exe`，SHA-256
  `7ae2ac2e5904ca330009af2827279d889906b0b9b7a8854c38eb707a56e955b5`。
- IDA 資料庫：`Orion2.exe.i64`，SHA-256
  `4a01791fcf877ed87a740a54748694ab34a02675e3117dac052aeaa3f883944e`。
- 工具：IDA Pro 9.4／IDAPython；位址是 DOS/4GW 映像的 IDA linear address。
- 可重生匯出：`tools/ida/audit_hotseat_ui.py`。匯出保留 raw 名稱、函式邊界、caller、
  指令 bytes 與資料／程式交叉參照，不以語意改名覆蓋原始定位。

## 已證實

- `sub_628E2 @ 0x628E2..0x62BB7` 只有一個直接 caller：
  `sub_1049B @ 0x1049B` 的 `0x10629`，屬該 jump table 的 case 16。
- 函式在 `0x628F4` 寫入 `word_1999AA=3`，以 `dword_19B874`／`dword_19B87C`
  取得兩個已載入物件，並由 640×480 減去物件寬高後除以二計算置中位置。
- `word_19B880` 是該流程中的目前索引；`byte_199CB1` 參與索引上限與相對席位計算。
  `0x629B8..0x62A72` 透過 `sub_7A990` 取文字 ID `0xA2..0xA5`，其中 `0xA3`
  會交給 `sprintf_` 組裝，再送入 `sub_77658` 的互動迴圈。
- `sub_626D6` 只在 `0x62B4B` 被此流程呼叫；單憑這個呼叫不能證明它是 remake
  逐回合「把鍵盤交給下一位」對話框的獨立繪製函式。

## 結論與證據等級

- **已證實**：`sub_628E2` 是原版熱座相關的完整互動流程，包含置中物件、席位索引、
  四個文字資源與確認／巡覽控制。
- **未知**：四個文字 ID 的完整原始字串、已載入物件的精確 LBX 來源，以及原版是否在每位
  玩家交令時另有完全遮蔽前一位畫面的專用 privacy gate。
- **推翻舊斷言**：`0x628E2` 不足以證明 remake 現有 320×200 視窗、`+14/+70`
  文字錨點及逐回合 TAKE OVER 對話就是原版精確畫面。舊註解不得再以原版座標陳述。

## Remake 映射與停止線

remake 保留逐席全畫面遮蔽與明確接手按鈕，因它防止下一位玩家在同機熱座中看到前一位
玩家的星圖與命令。這是玩家可見的隱私轉接設計，不冒稱原版逐像素還原。標題、玩家名模板、
席位模板、操作說明、結算提示、按鈕及轉場標籤必須由 `assets/i18n/ui.json` 提供；Go 只保存
語意鍵與 typed 席位資料。Windows 輸入 API 與原版 widget 內部不再深挖。
