# 原版忠實度重新稽核（2026-08-12）

## 結論

目前程式是可玩的 Go／Ebiten 4X remake，也有大量原版資料、畫面與部分公式接線；但核心玩法尚不能
宣稱已完成《銀河霸主 II》原版忠實重製。先前的完成判定常以「UI 可操作、存檔可保存、消費端存在、
單元測試通過」為主，這只能證明 remake 內部自洽。原版執行檔已提供具名函式與可查資料流時，仍有
多項玩法使用手冊概述或 LLM／工程設計補出的公式，甚至與 IDA Pro 直接可得的原版公式衝突。

本文件是重新忠實化的證據入口，不提供還原度百分比。完整現況以 `WORKLIST.md` 頂端活表為準。
可機械搜尋的逐系統狀態另存於 [`parity-matrix.tsv`](parity-matrix.tsv)；每一列分開記錄 remake 是否
可玩與原版 parity 的證據等級，禁止再用單一完成方框合併兩者。

## 輸入與工具

- 原版輸入：`Orion2.exe`，2,644,842 bytes，SHA-256
  `7ae2ac2e5904ca330009af2827279d889906b0b9b7a8854c38eb707a56e955b5`。
- 工具：IDA Pro 9.4，映像 `ida-pro-9.4-ver3:py312-v1`，IDC 與 Hex-Rays 9.4.0.260610。
- 位址基準：IDA 線性位址，`min_ea=0x10000`、`max_ea=0x1D5CD0`。
- 執行方式：唯讀掛載原版 EXE；每次由 EXE 在 Docker tmpfs 建立一次性 `.i64`，不修改正式資料庫。
- 探針：`tools/ida/re_audit_inventory.idc`、`tools/ida/re_audit_core.idc`。
- 原始稽核輸出只保存在本機 `/tmp/moo2-re-audit-20260812/`，不提交原版反組譯內容。

## 逆向工程實際深度

一次性 IDA 自動分析辨識 5,397 個函式；未套用外部符號前，只有 259 個函式不是自動 `sub_` 名稱。
原版內建符號解析表則有 8,589 筆，其中 4,201 筆為函式。這些符號是非常有價值的導航與模組分群
資料，但名稱本身不證明函式已完成語意、caller、consumer、欄位與分支研究。

本輪在專案文件與程式註解中抽到至少 120 次「近似」、115 次「未知」、5 次「代理值」與 4 次
「remake 模型」。這不是精確缺口總數，同一機制可能出現多次；它只能證明近似遍布核心玩法，不能
再以「零覆蓋函式見底」或「gameplay 子系統全接」推論原版 parity 已接近收尾。

## 已證實的反例

### 議會票數

- 原始定位：外部符號索引 `Calc_Council_Vote_`；目前 `.i64` 保留的原始名稱與線性位址為
  `sub_15B90 @ 0x15B90`，函式範圍 `0x15B90..0x15BCD`。
- 輸入：`Orion2.exe`，SHA-256
  `7ae2ac2e5904ca330009af2827279d889906b0b9b7a8854c38eb707a56e955b5`；工具為
  IDA Pro 9.4／IDAPython，位址基準為 DOS/4GW LE object #1、IDA 線性位址，程式碼基底
  `0x10000`。唯讀探針為 [`tools/ida/audit_council_vote.py`](../../tools/ida/audit_council_vote.py)，
  在 tmpfs 的 `.i64` 副本執行，不改名、不加型別、不儲存資料庫。
- 原始指令資料流：`0x15B94..0x15BAA` 將 `AL` 零擴充為帝國索引，以 `0xEA9` record stride
  讀取 `[player_base + index*0xEA9 + 0xA6]` 的有號 16 位值；`0x15BAF..0x15BC7` 以有號除法
  除以 10，餘數非零即把商加 1。
- 唯一直接呼叫端 `sub_156D4 @ 0x156D4` 在 `0x158A2` 從有效帝國索引陣列取出 `AL`，於
  `0x158A9` 呼叫本函式，再把 `AX` 累加至 `word_19A0D6` 並寫入
  `word_19A020[index*2]`。因此這是實際議會計票與總票數資料流，不是顯示 helper。
- 已證實公式：對正人口 `votes = ceil(population / 10)`。負人口不是正常玩家狀態；remake
  的非正值回傳 0 屬輸入安全政策，不宣稱原版負值行為。
- remake 消費端：`internal/gamedata/council.go` 的 `CouncilVotes` 已採同一公式；
  `internal/shell/council.go` 的候選排序、總票數、搖擺票與狀態顯示共用該函式，沒有第二套換算。
- 判定：**此換算切片已對齊**。候選、棄權、外交投票與排程仍須各自完成 RE，不能由本切片外推。

### 議會召開條件與下一屆排程

- 原始定位：`Check_For_Council_Meeting_ @ 0x168AF`。
- 已證實資料流：檢查目前年份／回合至少跨過 25、下一屆欄位、議會旗標、存續帝國數大於 2，並
  統計有效殖民地是否達全部殖民地的一半；召開後由目前時間寫回下一屆欄位。
- 2026-08-24 後續稽核已以 raw 指令閉合相對回合 25、後續間隔 25、三帝國與奇數星向下取整，
  Go 已移除固定 8 回合。完整證據、規格與剩餘投票差異見 `council-schedule-audit-20260824.md`。

### 外交評分與 AI 對 AI 談判

- 原始定位：`Diplomacy_Test_ @ 0x53146`、`NPC_To_NPC_Treaty_Negotiations_ @ 0x2552D`、
  `Change_Relations_ @ 0x4E3B5`。
- 已證實形狀：`Diplomacy_Test_` 讀政府／性格修正表、四組逐對手記錄、隨機值、種族能力與領袖／
  帝國欄位，最後使用 `-75/-50/0` 分桶；AI 對 AI 函式另依難度、正式條約、協議、共同敵人、
  第三方戰爭、關係與軍力等欄位執行完整談判流程。
- 目前 Go：`internal/diplomacy` 明示整套分數、17 級映射、漂移與事件值是「設計性重建」；
  `advanceAIDiplomacy` 主要由軍力差漂移，`ai_vs_ai.go` 是可保存的 remake 模型。
- 判定：**功能存在，但不是原版外交模型**。先前「完整 AI 接受表非阻塞」的分類不成立；外交是
  玩家可見核心玩法，應重新列為忠實化主線。

## 造成錯判的方法問題

1. 把「元件／畫面／按鈕／存檔欄位存在」當成原版效果已接。
2. 用 remake 自己的單元測試鎖住自編公式，再把綠色測試當 parity 證據。
3. 手冊沒有精確值時直接設計合理數字，沒有先查原版具名函式。
4. 把外部符號名稱、資料表名稱或函式名稱當成已理解完整資料流。
5. 把「remake 功能不阻塞發行」誤寫成「原版 oracle 不阻塞」，使核心玩法差異被降為可選研究。
6. 以零消費常數、固定參數與函式名稱掃描宣布「探針見底」，但沒有建立玩家機制到原版 call graph
   的完整清單。

## 新的忠實化閘門

每個玩家機制必須有一列證據矩陣，至少包含：

1. 原版具名入口與所有直接 caller；若符號表已有函式，禁止以「手冊沒寫」跳過 IDA。
2. 主要子呼叫、資料表、結構欄位、亂數 helper、分支與回寫欄位。
3. Go typed data、規則、快速／戰術或玩家／AI 等平行路徑、UI、存檔消費端。
4. 同輸入、同邊界值、同 RNG 的固定測試；必要時再做 DOSBox 動態 oracle。
5. 證據等級與尚未對回部分。只有整條垂直鏈閉合才能標「原版已證實」。

純 remake 現代化功能（TCP、TLS、文字安全框、跨平台封裝）仍可獨立標完成，但不能提高玩法忠實度
宣稱。下一輪按 `WORKLIST.md` 的重新忠實化順序執行，不再從舊 `[x]` 推導完成範圍。
